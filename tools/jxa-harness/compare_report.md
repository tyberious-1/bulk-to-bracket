# Before/after comparison: role-first, pip-based mana base vs. the old EDHREC-population-average logic

Generated by `tools/jxa-harness/compare.js`, run offline against the real fetched data in
`tools/jxa-harness/owned_raw.json` (6229 owned cards) and `tools/jxa-harness/prefetch_data.json`
(real EDHREC + Scryfall data for both sample commanders). No network calls were made for this
comparison.

- **Before**: `js/build/manabase.js` / `js/build/type-plan.js` / `js/build/deck.js` as of commit
  `3b0dc2c` (immediately before Task 2's first commit `7674c90`, "Add parsePips mana-cost parser"
  — i.e. the last commit before any of this plan's pip-based rework).
- **After**: the current branch tip, including the per-color floor fix described below (this
  report originally showed a real regression at the branch tip through Task 10's commit; the
  numbers below are the corrected, re-validated ones — see "Regression found, fixed, and
  re-validated" for the original numbers and what changed).
- Deck size: 99 cards (library only; the commander sits in the command zone and isn't drawn).
- Opening-hand rates: 2000 simulated draws per commander per run, 7-card hand, one mulligan-to-6
  if the initial 7 has no land at all. Because this is a stochastic simulation (not a closed-form
  calculation), the reported rate carries roughly ±1-1.5 percentage points of run-to-run sampling
  noise at 2000 trials — treat swings smaller than that as noise, not signal.

## Reading the numbers

**Krydle is a clean win, within noise.** Land count ticks up by one, both colors' source counts
hold flat or tick up by one, and both opening-hand rates are unchanged within simulation noise
(B: -0.3 to +0.1pp, U: +1 to +1.5pp) across the fix iterations below. Nothing here suggests the
pip-based math made anything worse for this commander, before or after the floor fix.

**Rivaz initially showed a real regression in black — since fixed and re-validated.** See
"Regression found, fixed, and re-validated" below for the full story. The numbers in the table
above are post-fix: black's opening-hand rate now sits at ~83.9-85.5% against an 87.2% baseline
(within 1.7-3.3pp, largely inside this simulation's own noise band), and red's rate settled at
~88.5-88.6% against an 86.7% baseline (a small, reasonable gain, not the outsized +5.5pp the
unfixed code produced). Source counts moved from an even 24/24 split to 23/26 — a mild, defensible
tilt toward red (the deck's spells do skew slightly red-heavy), not the 18/30 split that put the
commander's own black pip at real risk.

## Regression found, fixed, and re-validated

The first "after" run (branch tip through Task 10, before this fix) showed black's sources cut from
24 to **18** and its opening-hand rate fall from 87.2% to **76.55%** (about -10.6 percentage points,
reproduced three times) — while red rose from 24 sources / 86.7% to 30 sources / 92.25%. Both runs
used identical owned-card and EDHREC input data, and an 18-vs-24-source gap is far larger than the
~1-1.5pp sampling noise at 2000 trials, so this was a real structural effect of the code, not a
simulation fluke.

**Root cause:** `computeColorSourceTargets`'s per-color floor (`js/build/manabase.js`) was a flat
`max(8, 12% of landCount)` regardless of how many colors share the identity — meant to guarantee a
one-card splash is castable, not to protect a *primary* color of a small identity. Rivaz's own cost
is `{1}{B}{R}`: one black pip needed as early as turn 2-3. But the deck's other 59 nonland spells
happened to skew red-heavy in aggregate pip count, and with only an 8-source floor standing between
black and the rest of the pip-proportional split, black got pushed down to a rate meaningfully worse
than the old, color-identity-only heuristic — exactly the tradeoff the original task brief warned a
land-count/curve change could produce ("looks more correct on paper, measurably worse in practice").

**Fix:** scaled the floor by identity color count — `max(8, 12% of landCount, landCount / (colorCount
+ 0.5))` — so a 2-color identity gets a much stronger floor (16 sources for this 39-land deck, up
from 8) while a 5-color identity is unaffected (`Math.round(landCount / 5.5) <= 8` for every
landCount up to 42, so the existing splash behavior — including the overflow handling for 5-color
decks at a low land count — is unchanged). A 4-color identity gets a small bump too at the higher
end of the land-count range (`Math.round(landCount / 4.5)` is 9, not 8, for landCount 39-42, a
range real 4-color EDH decks do reach) — not the "unaffected" case, but a one-source difference that
neither overflows nor breaks anything; it just wasn't a case this harness's two sample commanders
(both 2-color) exercised, so it's flagged here rather than measured. Two constants were tried and
measured against this same harness before settling on the final one:

| Floor formula | Rivaz B sources | Rivaz B opening-hand rate |
|---|---|---|
| `landCount / (colorCount + 1)` (13 for this deck) | 20 | 81.15% |
| `landCount / (colorCount + 0.5)` (16 for this deck, **chosen**) | 23 | 83.9-85.5% (reproduced twice) |

The second, stronger constant recovered nearly all of the regression without touching Krydle's
already-clean result (Krydle's own floor moves from 8 to 13 (K=1) or 16 (K=0.5) depending on the
constant tried, but its two colors were never lopsided enough for the floor to bind either way).
The full unit-test suite (42 tests across `manabase`/`type-plan`/`smoke`) passes with the final
constant, including two new tests locking in the stronger two-color floor.

**Recommendation:** ship as fixed. The remaining ~2-3 point gap between Rivaz's fixed rate and its
old-heuristic baseline is within this simulation's own noise band at 2000 trials, and further
narrowing it would mean weakening the pip-weighting that made Krydle's result genuinely better —
not worth trading away for a difference this size. A future session could re-run this same harness
with more sample commanders (only two are prefetched today) to check the floor formula holds up
across a wider color-count/pip-skew range before this change sees heavier real-world use.

## Harness fixes made while building this comparison

Three gaps in the Task 10 harness surfaced only once real async project code ran end-to-end under
`osascript -l JavaScript`, and were fixed (not worked around) so the comparison could run at all:

1. **`tools/jxa-harness/prelude.js`**: JXA's built-in `console` object only implements `.log`;
   `js/api/edhrec.js`'s error paths (e.g. `fetchEdhrecThemePage`, hit constantly here since this
   harness never prefetched the EDHREC theme sub-pages) call `console.warn`/`console.error`, which
   threw `console.warn is not a function`. Added `console.warn = console.log` / `console.error =
   console.log` fallbacks, consistent with the other environment stubs already in that file. This
   is a harness-only change; no project source was touched.
2. **`tools/jxa-harness/compare.js`**'s `collection` object: the brief's draft built it as
   `{ entries: [...] }`, but `hasOwnedCard()` (`js/collection/csv.js`) requires
   `collectionData.byNormalized` (a `Map<normalizedName, quantity>`), which threw `undefined is not
   an object (evaluating 'collectionData.byNormalized.has')`. Rebuilt the collection object here to
   match `parseCSV`'s real output shape (`byNormalized`, `byFrontFace`, `entries`, `originals`,
   `uniqueRawNames`), derived from `owned_raw.json` the same way `parseCSV` derives it from CSV rows.
3. **`summarize()`'s role counting**: calling `getRoleContributions(card)` directly on a
   `finalDeck` entry always returns `[]` — deck entries (`js/build/deck.js`'s `addCard`) carry only
   `name/type/cmc/colors/score/source/roles`, never oracle text, so `getCardText` is `""` for them.
   This is the exact, previously-diagnosed bug behind `getSupportPackageCounts.total` always being 0
   (see project memory `deck-entries-carry-no-oracle-text`). `deck.js` already works around it by
   precomputing `.roles` once at push time; `summarize()` now reads that precomputed field
   (`card.roles || []`) instead of silently reproducing the bug. Without this fix, every run (before
   and after) printed `Roles: {"ramp":0,"draw":0,"removal":0,"wipe":0,"synergy":60}` for every
   commander — a uniformly wrong number, not a real result.

None of these three fixes touch card-selection or mana-base logic; they only make the measurement
itself correct.
